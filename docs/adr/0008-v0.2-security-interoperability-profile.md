# ADR-0008 -- v0.2 Security Interoperability Profile

Status: Accepted

## Decision

v0.2.0 starts with an interoperability proof, not a production security
rollout. The proof covers Go Conveyance, .NET 10 Windows, and .NET 10 iPhone
on a real target runtime. Production enrollment, recovery, revocation,
Channel Key Grant APIs, payload-encryption integration, and foreign-context
integration remain deferred until a passing result and Control-Plane review.

The complete candidate profile is specified in `docs/15_SECURITY_INTEROP_PROFILE.md`.
The Channel Key Grant and `protected_payload` framing in that document are
v0.2 interoperability candidates, not published HTTP/API contracts; the
v0.1 Current Object contract remains unchanged.

## Frozen candidates

- Installation authentication is TLS 1.3 mutual TLS using a distinct
  per-Installation X.509 v3 ECDSA P-256 credential, SHA-256 certificate
  signature, Digital Signature Key Usage, and TLS Web Client Authentication
  EKU. The spike uses an explicit pre-enrolled
  `(trust_domain_ref, installation_ref)` to installation-authentication-SPKI
  fingerprint mapping as fixture evidence, not as the future enrollment
  protocol.
- Installation authentication, WGT DeviceIdentity, Key Encryption Credential,
  Channel Key, and Recovery Material are separate. The mTLS key is never the
  HPKE recipient key.
- Channel Key Grants use HPKE RFC 9180 Base Mode with DHKEM(X25519,
  HKDF-SHA256), KDF HKDF-SHA256, and AES-256-GCM (`kem_id=32`, `kdf_id=1`,
  `aead_id=2`). The exact Grant 1.0 JSON, info, AAD, raw 32-byte plaintext,
  and Base64 rules are frozen as an interoperability candidate.
- Envelope protection candidates use AES-256-GCM with a 32-byte Channel Key,
  12-byte nonce, 16-byte tag, and `nonce || ciphertext || tag` framing. The
  exact canonical Envelope AAD and deterministic fixture inputs are frozen;
  expected ciphertext is intentionally not yet frozen.
- Real-iPhone Keychain-backed mTLS and HPKE behavior are required. Library or
  native-bridge selection remains empirical and must satisfy the exact
  vectors and runtime gates.

## Constraints and consequences

Use standard reviewed primitives only. No homemade crypto fallback is
allowed if HPKE or iPhone mTLS fails. Production nonce strategy is deferred.
Enrollment and recovery protocols are deferred. Replay protection remains
the ADR-0006 client checkpoint rule rather than an AEAD claim.

The result is `PASS`, `BLOCKED-HPKE`, `BLOCKED-MTLS-IOS`,
`BLOCKED-KEY-STORAGE`, or `BLOCKED-OTHER`, with exact evidence for every
blocked result. No partial result may be called production-ready security.
